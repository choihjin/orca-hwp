# 메모 보기 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> 이 저장소에서는 Orca 워커가 아래 "분담"대로 나눠 맡을 수 있다. 자기 Task만 읽어도 되게 Interfaces를 적었다.

**Goal:** 문서의 메모를 하나도 빠뜨리지 않고 옆 목록과 쪽 위 강조로 보여 주고, 에이전트에게 JSON과 강조된 PNG로 준다.

**Architecture:** rhwp 0.8.7에 메모 읽기 패치를 더한 `0.8.7-p2`가 `getMemos()` JSON을 낸다. DOM 없는 JS 모듈이 이를 묶음과 강조 사각형으로 바꾸고, 뷰어와 `agent-view`가 그 모듈을 함께 쓴다.

**Tech Stack:** Rust 1.93.1 + wasm-pack 0.15.0(이미 설치됨), ESM JavaScript + JSDoc(공용 코드), TypeScript(프레임 코드), `orca/testing`, Node 22.

**Spec:** `docs/superpowers/specs/2026-11-24-memo-list-design.md`

## Global Constraints

- 권한 없음(`capabilities: []`), 네트워크 없음. 새 실행 의존성을 더하지 않는다.
- 파일 상한: WASM·JS 파일당 16,777,216 B, 플러그인 폴더 52,428,800 B·2,000파일.
- 태그에 들어갈 트리에 `.hwp`, `.hwpx`, 그 밖의 바이너리를 커밋하지 않는다(허용: png·jpg·webp·gif·woff·woff2·wasm). 400자가 넘는 base64 문자열도 두지 않는다.
- rhwp를 import하는 모듈은 `editor/engine/rhwp-adapter.js` 하나뿐. 공용 모듈은 변환 없이 도는 ESM JavaScript.
- 엔진 바탕은 rhwp `v0.8.7`(`1a76570e833917d15817415a53c09ad61ab3203f`), 기존 패치 `v0.8.7-tac-sibling-reset.diff` 다음에 새 패치를 적용한다.
- 메모가 없는 문서: 쪽 SVG가 0.8.7-p1과 바이트까지 같고, 화면에 버튼도 목록도 없다.
- 메모 작성자·본문은 `textContent`(화면)와 XML 이스케이프(SVG)로만 쓴다.
- 예외: 테스트 파일은 가짜 엔진을 끼우려고 `rhwp.js`를 직접 import해도 된다.
- `fixtures/`의 비공개 문서는 열지 않는다.
- 커밋: `[TYPE] 한글 제목`(50자 이내, 마침표 없음), AI 기여자 문구 금지. 작업 브랜치에만 커밋하고 푸시·병합·태그·`dev load`는 사용자 승인 뒤에 한다.
- 새 worktree에서는 먼저 `orca plugin types .`와 `npm run fixtures`를 실행한다.

## Review Focus

- 메모가 달린 글이 줄이나 쪽을 넘는다: 줄마다 사각형이 나오고 쪽은 시작 글자의 쪽이다 → Task 3.
- 작성자·본문이 `<img onerror=…>` 같은 글이나 제어 문자를 담는다: 글자 그대로 보이고 제어 문자는 지워진다 → Task 2, 4, 5.
- 목록을 열어 둔 채 파일이 바뀐다: 이전 메모와 선택이 사라지고 새 메모가 나오며 닫은 상태는 유지된다 → Task 4.
- 본문이 빈 메모, 작성자가 없는 메모: 항목이 사라지지 않고 "(내용 없음)"·"(작성자 없음)"으로 보인다 → Task 4.
- 메모 수백 개와 수천 자 본문: 목록만 스크롤되고 첫 칠이 300 ms 넘게 늦어지지 않는다 → Task 6.

**Interfaces:**
- Produces: `HwpDocument.getMemos(): string`. JSON `{"memos": MemoEntry[], "problems": MemoProblem[]}`.
  - `MemoEntry = { number, author, text: string|null, date: string|null, dateText: string|null, place, anchorText, paragraphText, multiParagraph, anchorKey, sectionIndex: n|null, ownerParaIndex: n|null, paraIndex: n|null, path: {controlIndex,cellIndex,cellParaIndex}[]|null, startCharIdx: n|null, endCharIdx: n|null }`. 글자 위치는 코드 포인트 단위.
  - `place`: `body|tableCell|textBox|caption|header|footer|footnote|endnote|masterPage|unlinked`
  - `path`는 `getPageTextLayout`의 `cellPath`와 같은 모양(글상자는 `cellIndex: 0`). `body|tableCell|textBox`가 아니면 `paraIndex`·`path`·`startCharIdx`·`endCharIdx`는 `null`.
  - `ownerParaIndex`: 메모를 품은 구역 바로 아래 문단. `masterPage`·`unlinked`는 `null`.
  - `multiParagraph`면 `endCharIdx: null`, `anchorKey`는 메모마다 다르다(이 판에서는 끝을 구하지 않으므로 묶이지 않는다).
  - `date`: `MEMO/<…>/<번호>/<하위>/<상위>/…`의 FILETIME → `YYYY-MM-DDTHH:MM:SSZ`(UTC). FILETIME이 0이거나 없으면 `null`, 이때만 `dateText`에 HWPX `CreateDateTime` 원문.
  - `MemoProblem = {code:"no-body",count,number} | {code:"unlinked-body",count,number} | {code:"bad-record",count} | {code:"section-unreadable",count,sectionIndex} | {code:"missing-memo",count}`. 코드마다 항목 하나이고 `number`·`sectionIndex`는 첫 것이다. 출력 상한은 `memos`에만 적용하고 `problems`는 항상 남는다.
  - `missing-memo`: 파일에 선언된 메모 필드(HWP의 필드 `CTRL_HEADER` 가운데 메모이거나 명령이 `MEMO/`인 것, HWPX의 `fieldBegin type="MEMO"`)보다 찾은 것이 적거나 출력이 8 MiB를 넘어 빠진 수. 모르는 코드가 와도 JS는 메모를 잃지 않는다.
  - `anchorText`·`paragraphText`는 앞 2,000 코드 포인트까지. `place`는 강조할 수 없는 바깥(머리말 등) 안이면 바깥 이름.

### Task 3: 강조 위치와 쪽 찾기

**Files:** Create `editor/engine/memo-marks.js`, `editor/engine/memo-locate.js`, 각 `.test.mjs`. Modify `editor/engine/rhwp-adapter.js`, `editor/engine/rhwp-adapter.test.mjs`

**Interfaces:**
- Consumes: Task 2의 `MemoThread`, `buildMemoReport`.
- Produces:
  - `AnchorRun = { text, x, y, w, h, charX: number[], secIdx, paraIdx, charStart, parentParaIdx?: number, cellPath?: {controlIndex,cellIndex,cellParaIndex}[] }`
